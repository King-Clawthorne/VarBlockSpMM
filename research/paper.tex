\begin{abstract}
VarBlockSpMM is a standalone CUDA implementation of FP32 sparse-dense
products for matrices stored as packed dense blocks with variable sizes.
It avoids scalar expansion, fixed-block retiling, output atomics, and
execution-time temporary workspace. On one RTX 5060 Ti, a full-core
follow-up on three additional matrix seeds gives geometric
fastest-tested-library-to-direct time ratios of \RobustLatencyOverall{}
for individual products and \RobustQueuedOverall{} for batches of eight
queued products. The core contains 128 configurations spanning four panel
widths, four shape distributions, two locality patterns, and four degrees.
The kernel shares dense input tiles across rows and reuses sparse values
across RHS accumulators. Matched comparisons show that its narrow-panel
policy gives speedup factors of \RhsEightUpgrade{} at width 8 and
\RhsSixteenUpgrade{} at width 16 over the previous policy.
On the generated native component, the prepared-host startup ratio is
\NativeStartupRatio{} including one completed product, while the
steady-state BSR8 ratio is \NativeBsrRatio{} and favors BSR8.
Published-matrix and dense-library controls identify cases better served
by other representations. Verified build records and raw measurements
support separate comparisons of execution, startup, and storage, defining
the conditions under which retaining packed variable blocks is useful.
\end{abstract}

\section{Introduction}
Applications with dense variable blocks face a representation choice when
using sparse GPU libraries. Scalar CSR expands block metadata to individual
entries. Fixed-block BSR subdivides the original blocks and may require a
new value layout. Grouped GEMM can retain block shapes, but overlapping
contributions require separate calls or a reduction. VarBlockSpMM executes
the packed product directly, so an application can retain its block layout
and avoid these conversion steps.

This is useful when direct execution is faster, when scalar metadata is
costly, or when a matrix is used too few times to repay library conversion
and setup. We measure these benefits separately. The intended input has
dense stored blocks. Artificially grouping scattered scalar nonzeros can
instead waste storage and arithmetic, as the published-matrix controls show.

We study \(C=AB\), where \(A\in\mathbb{R}^{M\times K}\) is a packed
variable-block sparse row matrix and \(B\in\mathbb{R}^{K\times N}\) and
\(C\in\mathbb{R}^{M\times N}\) are column-major dense panels. The supported
block dimensions are \(8,16,\ldots,64\), with independently chosen row and
column partitions. Dense panel widths are \(N\in\{8,16,32,64\}\).
The implementation uses FP32 values and accumulation for non-transpose
multiplication with \(\alpha=1\) and \(\beta=0\).

The implementation specializes execution by panel width while retaining
runtime block dimensions. One CTA owns each block row, shares the dense
input tile, and writes the completed output once. This combines a small
execution plan with direct access to the application's packed values.

The contribution is a standalone execution policy for this packed format,
with an experimentally measured boundary against conversion-based library
alternatives. It combines full-panel accumulation for narrow RHS widths
with shape-dependent staging for wider panels, retaining one writer per
output and requiring no execution workspace. The matched experiments test
which choices improve this implementation. The library comparisons test
when their combined benefit exceeds the benefit of padding-free BSR8
subdivision or scalar CSR expansion. These are implementation and
measurement contributions. They do not establish a new sparse storage
model or an end-to-end application speedup.

Startup and storage measurements separately test the cost of adopting each
representation, with raw measurements tied to verified builds.
Figure~\ref{fig:use-cases} shows where the tested widths and workloads
favor direct execution.

\section{Related work}
Variable blocking is established prior art. Vuduc and Moon studied variable
and unaligned blocks for sparse matrix-vector multiplication [6]. OSKI defines
variable block row storage through independent logical row and column
partitions [7]. VarBlockSpMM uses this structural model for a dense
multi-column right operand on CUDA.

GPU SpMM work has examined row assignment, load balance, instruction-level
parallelism, and reuse. Yang, Bulu\c{c}, and Owens describe row-splitting and
merge-based approaches [1]. GE-SpMM caches sparse rows and merges warps to
reduce redundant loads [8]. Tensor-core methods such as Okanovic et al. trade
packing and preprocessing for dense matrix-instruction throughput [2].
These techniques motivate the present kernel, but this study does not
establish superiority over compatible research implementations.

The motivating application is adaptive construction of hierarchical
\(H^2\) matrices. Boukaram et al. describe a non-uniform batched BSR product
implemented through non-uniform batched GEMM operations [5]. The present
work addresses the underlying packed-block product. We add a generated covariance near-field component whose partitions come
from a spatial cluster tree. This tests a concrete dense-block component,
while excluding far-field compression and the complete construction pipeline.

NVIDIA provides scalar and fixed-block SpMM through cuSPARSE [3], and
per-group GEMM dimensions through grouped cuBLAS [4]. These form the
library controls. Asynchronous global-to-shared copies can overlap tile
movement and arithmetic [9]. These mechanisms are established techniques. We combine and evaluate them
for this particular variable-block operation.

\section{Representation and kernel}
Let block-row boundaries be \(r_0<\cdots<r_R\), and block-column boundaries
be \(c_0<\cdots<c_Q\). Block \((i,j)\) has height
\(h_i=r_{i+1}-r_i\) and width \(w_j=c_{j+1}-c_j\). Its column-major values
are packed without rounding its dimensions to a global block size, and its
contribution is
\[
C[r_i:r_{i+1},:] \mathrel{+}= A_{ij}B[c_j:c_{j+1},:].
\]
Block-row pointers and column indices locate the blocks. Scalar offsets and
value offsets are 64-bit. Block indices remain 32-bit. Host validation checks
monotonic offsets, dimensions, index bounds, and payload sizes. A matrix owns
its GPU storage and row classifications. Execution plans hold non-owning
views, so the matrix must outlive its plans.

\subsection{Output ownership and accumulation}
One cooperative thread array, or CTA, owns one block row at every supported
RHS width. Threads outside the actual row height do no output work. Each
active thread accumulates all contributions to its outputs and writes them
once. CTAs never update the same scalar, so execution needs neither output
atomics nor partial-output reduction storage. Work imbalance between rows
can still limit performance.

RHS 8 and 16 use 64-thread CTAs, with each active thread owning all RHS
columns of one scalar row. RHS 32 assigns eight output columns per thread,
and RHS 64 assigns sixteen. Multiple accumulators let each loaded sparse
value feed independent multiply-add operations. Their register cost must
be balanced against the number of resident CTAs and active threads.

\subsection{Full-panel accumulation for RHS 8 and 16}
The narrow-panel kernel launches one 64-thread CTA per block row. Thread
\(t<h_i\) owns \(C[r_i+t,0:N]\), with \(N\) FP32 accumulators. For each
stored block, all 64 threads cooperatively load its \(w_j\times N\) input
tile into shared memory. A barrier makes that tile visible before use.
Each active thread then loads one sparse value at a time and reuses it
across all \(N\) columns. A second barrier protects shared-memory reuse
when another block follows.

The shared leading dimension is 65 floats. The RHS-8 and RHS-16 kernels
allocate 2,080 and 4,160 shared-memory bytes per CTA, respectively. Since
the largest supported row has 64 scalars, one CTA covers the entire panel
without a row-size threshold or a second output tile. Empty rows write zero.

The narrow policy was selected on development seed 4 at 256, 1,024, and
4,096 block rows, degrees 2 and 16, and all four shape distributions. We
compared staged kernels with different thread and accumulator counts and
warp-reduction candidates, checking every output against a full CPU reference.
The final policy uses full-panel accumulation and staging at both widths.
Evaluation seeds are separate from this development seed. The matched
campaign also measures the previous narrow policy in the same executable
and process, so its improvement does not depend on comparing archived times.

\subsection{Staging and dispatch}
At every supported width, each local output row consumes the same dense input tile
for a stored block. Cooperative staging loads this tile once per CTA and
reuses it across local rows. A shared leading dimension of 65 floats reduces
power-of-two bank-alignment conflicts. The synchronous RHS-32 and RHS-64
kernels use 8,320 and 16,640 shared-memory bytes per CTA, respectively.
The narrow kernels use the smaller CTAs described above. RHS 32 and 64
retain their width-specific staging and buffering policies.

For RHS 32, rows of at most 16 scalars use a 128-thread single-buffer CTA.
Taller rows use a 256-thread CTA with two tiles, consuming 16,640 shared-memory
bytes. The next input tile is prefetched before arithmetic on the current
tile. Pipeline waits and CTA barriers protect visibility and buffer reuse.
A mixed-height matrix is split into two launches only when its mean block
degree is at least eight. Homogeneous matrices need only the applicable
launch. At lower mean degree, the mixed matrix uses the unsplit policy.

Double buffering is not enabled for RHS 64. A development experiment increased
shared allocation to about 32.5 KiB per CTA and regressed a representative
median from 2.891 to 4.419 ms. This observation motivated a width-specific
policy rather than a universal pipeline. All dispatch thresholds were selected
from development sweeps and held fixed for the main library comparison.

\section{Experimental design}
The main campaign measures the optimized dispatch described above against
persistent library controls. All synthetic and application measurements were
collected with the current implementation. The separate kernel ablations
compare direct implementations under their stated protocols.

\subsection{Persistent library controls}
\textbf{Scalar CSR.} Synthetic dense blocks are expanded into scalar CSR
once. Plans retain arrays, descriptors, handles, and workspace. We measure
the default algorithm, explicit CSR algorithm 1 with preprocessing,
algorithm 2, and algorithm 3 with preprocessing. All use FP32 compute,
column-major panels, and the same non-transpose operation. Preprocessing and
initial descriptor creation occur during setup or warmup, outside timing.
NVIDIA documents preprocessing benefits for algorithms 1 and 3 [3].

The \emph{CSR lower envelope} is the minimum GPU median among those four
configurations within each process. Selecting on measured data favors this comparator. The envelope has no
deployed tuning policy or charged tuning cost. It lets us check whether
a direct-method win depends on the default library algorithm. Host ratios use a separate
minimum over host medians, so they need not select the same algorithm.

\textbf{Grouped cuBLAS.} Blocks with equal height and width are grouped within
each ordinal block slot. A slot contains at most one block from each row, so
its GEMM outputs do not overlap. Slots execute sequentially. The first uses
\(\beta=0\), and subsequent slots use \(\beta=1\). The handle, packed values,
shape groups, and device pointer arrays persist.

The cached control refreshes input and output pointer arrays only when their
base addresses change. It omits the full output clear when every row is
nonempty. For matrices containing empty rows it retains the clear to initialize
those rows. A separate changing-address experiment alternates between two
allocated input/output pairs and includes pointer refreshes. It is paired
with a direct method that alternates the same pairs. A stream-ordered CUDA kernel computes the input and output pointer arrays
from persistent device offsets when needed. This avoids relying on the
lifetime or staging behavior of temporary pageable host arrays.
The first measured call reuses the final warmup addresses. The remaining
19 calls alternate addresses and refresh the grouped pointers.
Changing-address timing includes these pointer-generation launches.
The slot decomposition still incurs sequential GEMM calls and repeated
output traffic, so it is a specific library composition rather than an
oracle over possible grouped algorithms.

\textbf{Fixed-block BSR.} The uniform-32 synthetic subset is also measured
with cuSPARSE BSR algorithm 1. Block values are converted to the required
row-major block layout outside timing, while dense panels remain column-major.
This gives a format-matched control where variable blocking is unnecessary.

\textbf{Subdivided BSR8.} Every supported dimension is divisible by eight.
We therefore also subdivide each stored variable block into 8-by-8 blocks
and measure cuSPARSE BSR algorithm 1 on every input. The scalar matrix and
stored scalar count are unchanged, and no padding is introduced. A block
of shape \(h\times w\) becomes \((h/8)(w/8)\) fixed blocks, increasing
block metadata while exposing a different scheduling and reuse tradeoff.
Conversion to row-major BSR tiles occurs outside steady-state timing.
The published scalar inputs retain their internal zeros in this control,
whereas compact CSR removes them. BSR8 measures the effect of subdivision, while compact CSR measures the
benefit of removing internal zeros.

\subsection{Synthetic workloads}
The core grid contains 128 configurations with 4,096 block rows and columns,
degrees \(2,4,8,16\), four panel widths, four size distributions, and two
locality patterns. Uniform uses size 32. Low variance samples
\(\{24,32,40\}\), high variance samples \(\{8,16,\ldots,64\}\), and bimodal
samples \(\{8,16,48,64\}\). Row and column dimensions are drawn independently.
Every row in the core grid has exactly the requested degree. Columns are
sampled without replacement and sorted. Random locality spans all block
columns. Local locality samples cyclic offsets within plus or minus the
requested degree. Stored values are uniform on \([-1,1]\).

The extension adds 40 configurations. It evaluates 256, 1,024, and 4,096
block rows and columns for high-variance and bimodal sizes, random locality,
all panel widths, and either constant degree 16 or the repeating degree pattern
\(0,1,16,16\). The latter has mean degree 8.25 and explicitly includes empty
rows. It is constructed by retaining zero blocks, one block, or all blocks
from successive rows of the degree-16 parent matrix. Eight constant-degree
4,096-row configurations already belong to the core grid. Thus the union
contains 168 unique configurations.

The synthetic campaign holds matrix seed 1 fixed and repeats each configuration in
three fresh processes. The dense input contains independent pseudorandom
uniform values on \([-1,1]\), generated with seed 9123. Changing-address
buffers contain identical values to isolate address-dependent work.

\subsection{Published matrices and partitioning}
We also test BCSSTK13, BCSSTK14, and BCSSTK15 from the Harwell-Boeing
collection, downloaded through SuiteSparse [10]. They originate from fluid-flow
eigenvalues, the Omni Coliseum roof, and an offshore platform module,
respectively [11]. Their original orders are 2,003, 1,806, and 3,948.

Symmetric Matrix Market input is expanded, duplicates are combined, and
explicit zeros are removed. Values are divided by the maximum absolute
entry and converted to FP32. The rows and columns are padded only at the
outer boundary to the next multiple of eight. In the original scalar ordering,
row partitions cycle through \(8,16,32,64\) and column partitions through
\(64,32,16,8\). The final partition is truncated to the remaining multiple
of eight. A block is stored if it contains a source nonzero. Other entries
inside that block are represented as zeros.

This deterministic procedure preserves application-derived values and
sparsity after normalization, but uses artificial partitions in place of native
finite-element or hierarchical partitions. The measured compact-CSR controls retain only
source nonzeros in the padded scalar domain, using explicit algorithms 1,
2, and 3 with preprocessing for 1 and 3. Their lower envelope is computed
as above. Cached grouped cuBLAS uses the identical packed blocks as the
direct method. This separates the cost of block fill from scalar sparse
execution. All four panel widths and three fresh processes are retained. The partitions
have 68, 61, and 132 block rows, respectively. RHS 8 and 16 use the same
64-thread staged kernel as the synthetic inputs.

\subsection{Geometry-derived covariance near field}
We construct the dense near-field component of a spatial covariance
operator, following the bounding-box admissibility model described by
Boukaram et al. [5]. Unlike grouping a pre-existing scalar sparse matrix,
the spatial tree defines the dense blocks before matrix assembly.

Each input contains 2,048 or 8,192 points in three dimensions. Uniform
geometry samples the unit cube. Clustered geometry places three quarters
of the points in a clipped normal cloud with coordinate mean 0.3 and
standard deviation 0.07, and leaves the remaining quarter uniform.
Independent NumPy generator seeds 1, 2, and 3 give twelve matrices.
For each matrix and panel width, three fresh processes repeat the same
instance, giving 144 process observations.

A binary spatial tree splits along the longest bounding-box axis, using
a stable coordinate sort and a midpoint rounded to a multiple of eight.
A leaf stops at eight points, or at no more than 64 points when its
bounding-box diameter is at most 0.18. Eight-point granularity is an
explicit restriction of this application model. No points are padded,
dropped, or grouped after scalar matrix assembly. The reordered leaf
indices define both partitions. Uniform geometry at 2,048 points produces
only size-eight leaves and is retained as a useful fixed-block control.

For leaf boxes \(s,t\), let \(D\) denote Euclidean box diameter and
\(\operatorname{dist}\) the minimum Euclidean distance between boxes.
We retain leaf pairs failing
\[
  \frac{D(s)+D(t)}{2}\leq 0.5\operatorname{dist}(s,t).
\]
Each retained block stores the Gaussian covariance entries
\[
 A_{ij}=P^{-1/2}\exp\bigl(-\|x_i-x_j\|^2/(2(0.1)^2)\bigr),
\]
where \(P\) is the point count. The amplitude fixes the numerical scale
across sizes. Other blocks are zero in this component. The far-field
component of the full covariance operator is outside this experiment.
The resulting near-field component need not itself be positive definite.

An independent scalar-row enumeration recomputes the covariance values
and provides the compact-CSR CPU reference. Preparation checks every
packed block against this reference exactly in FP32. All stored values
are nonzero for these inputs. Thus the experiment has full block fill
and tests native spatial partitions within this specified model. It is
not a production solver trace or an end-to-end hierarchical computation.

Some near-field inputs occupy a large fraction of the scalar matrix.
We therefore include a persistent dense cuBLAS SGEMM control on all
native and published-matrix inputs. It expands the compact scalar source
to a zero-filled column-major dense matrix during startup, retains that
matrix and a handle, and uses the same non-transpose operation and
default cuBLAS math contract as the grouped control. Its output passes
the same full-reference tolerances. Dense expansion is impractical at
the main synthetic grid's scalar dimensions and is not attempted there.

\subsection{Matched mechanism experiments}
The matched campaign crosses 256 and 1,024 block rows, degrees 2 and 16,
high-variance and bimodal shapes, and four RHS widths with random locality.
Each of the 32 configurations uses three matrix seeds and three fresh
processes per seed, giving 288 processes. Both instance and process
variation are therefore present, without treating timing trials as
independent matrix samples.

For RHS 8, a complete \(2\times2\times2\) factorial design varies
linear versus eight-row output mapping, one versus two accumulators, and
one versus two CTAs per block row. Every CTA has 256 threads. For wider
panels, a global-load four-accumulator control and the selected wider
accumulator count both use one 256-thread CTA per row. Cooperative staging
is compared with direct loads using the same output mapping and CTA size.
Single and double buffering use the same indirect row order, CTA size,
and accumulator count. At RHS 8 and 16, an additional pair compares global and shared input
loads with identical 64-thread CTAs and full-panel accumulators. The previous
narrow policy and the production dispatch are measured alongside these
controls. Each variant is checked against a full double-accumulating
CPU reference, rather than only sampled output probes.

These comparisons isolate the named policy choices at fixed input and
launch dimensions. Register allocation, instruction scheduling, and active
thread count can change as consequences of a choice. They are not held
artificially constant. The factorial marginal effects average across
the other two RHS-8 factors, and the retained per-variant timings expose
interactions rather than assuming that speedups multiply.

\subsection{Timing and correctness}
Each method receives five warmups and 20 measured executions. Methods are
randomly ordered within each process. Configuration and process-label jobs
are shuffled before serial execution, with one GPU benchmark active at a
time. Synthetic order uses seed 20260905, published-matrix order uses 20260906,
and both supplementary campaigns use 20260907.
Three process labels identify repeated observations of the same matrix,
rather than three different matrix instances.

CUDA events bracket each execute call on the default stream, followed by an
end-event synchronization. Synchronized host durations are also retained.
The intervals measure execution calls, including any device idle time while
the host submits later work. This matters particularly for library compositions
with multiple calls, so the intervals do not isolate kernel-instruction time.
Allocation, format conversion, initial input transfer, and correctness
validation are excluded. Output buffers are poisoned before each method's warmups, and correctness
is checked both after warmup and after measurement. Every raw GPU and host
duration, method position, command, executable checksum, and process status
is saved. Medians use the mean of the two middle
observations for an even sample count.

The revision uses the RTX 5060 Ti with compute capability 12.0, CUDA runtime
and driver API 13.4, Windows, MSVC 19.44, Release compilation, native CUDA
architecture, and fast FP32 math. The Windows display driver reports version
32.0.16.1656. The GPU is not clock-locked or isolated from all operating-system
activity. Per-process environment records accompany the synthetic timings.

The correctness suite covers both localities for every combination of four
size distributions, four widths, and degrees \(1,4,8,16\), giving 128 cases.
Sixteen additional cases contain an empty first row. It tests explicit CSR algorithms, BSR32 and BSR8, cached pointer reuse,
changed input and output addresses, and non-default streams. Deterministic
tests cover all 64 block shapes at every RHS width, mixed empty rows,
and completely empty matrices. NaN initialization before every comparison
detects missing writes, and a deliberately empty operation must fail the
comparison helper. Queued pointer changes are checked without intervening
host synchronization. Every CUDA status in the test execution path is checked. Full output is compared with a CPU reference that accumulates the entire
dot product in double before one final FP32 cast. Failure thresholds are maximum absolute error \(5\times10^{-4}\)
or relative \(\ell_2\) error \(5\times10^{-5}\), with NaN and infinity rejected.

Each timed synthetic matrix also receives 64 CPU output probes per method
outside timing. Every application output is checked against a separate
compact-CSR CPU reference, which also tests the packing transformation.
The expanded test executable also passes Compute Sanitizer memcheck with
zero reported errors. Racecheck restricted to the project's row-owned and pointer-refresh kernels
reports zero hazards. Library kernels are outside that racecheck filter.
These checks do not substitute for sanitizer coverage of every timed configuration.

\subsection{Startup, storage, and repeated products}
On native inputs, each method records synchronized host startup time from
its prepared host representation through construction, GPU transfer,
library initialization or preprocessing, and one completed product.
Common input and output buffers and the CUDA context already exist.
Matrix storage is constructed separately for each method, and method order
is randomized. This measures application-level startup within an existing
CUDA process, not cold driver initialization. Correctness work is excluded.

Persistent storage counts the explicitly allocated device arrays, including
matrix values and indices, row classifications, pointer and offset arrays,
and the workspace requested through cuSPARSE. It excludes common dense
panels, host-side metadata, allocator overhead, and opaque library-internal
allocations. In particular, grouped cuBLAS storage is not presented as a
measurement of its handle's internal memory use.

For \(k\) products, we report the cost model
\(T_m(k)=S_m+(k-1)H_m\), where \(S_m\) is startup including the first
product and \(H_m\) is the synchronized host median for subsequent calls.
A second model adds measured host geometry and representation assembly.
Direct, BSR8, and grouped methods start from packed blocks, while compact
CSR and the dense control use the separately timed scalar assembly.
Dense expansion is included in its startup observation. The preparation script
records one CPU assembly observation per matrix, not a distribution.
These are amortization estimates for serial synchronized calls, not timed
solver runs, CUDA-graph execution, or asynchronous throughput measurements.
For each \(k\), the comparator is the lowest total among all measured
library methods. No tuning cost is charged to that lower envelope.

\subsection{Aggregation and uncertainty}
For configuration \(c\), process label \(p\), comparator \(b\), and direct
method \(d\), let
\[
 y_{c,p}=\log\left(t_{b,c,p}/t_{d,c,p}\right),\qquad
 g_c=\exp\left(\frac{1}{3}\sum_{p=1}^{3}y_{c,p}\right).
\]
The reported geometric mean is
\(G=\exp(|\mathcal C|^{-1}\sum_{c\in\mathcal C}\log g_c)\).
Each configuration and each process within it has equal weight. Ratios
above one favor the direct method. Minima and win counts refer to the
configuration ratios \(g_c\), not to individual timing trials.

We also report the range of three aggregate ratios obtained by holding the
process label fixed. This is a descriptive repeatability check, not a
confidence interval or a test of significance. Three process observations
provide limited information about tails and shared thermal drift. No
population-level confidence interval is assigned to this deliberately chosen
grid, and no comparison of interval widths is interpreted as a decomposition
of uncertainty. Matrix-instance variation, workload selection, process noise,
and hardware variation remain distinct questions.

\section{Scope and limitations}
Measurements cover one GPU and one local operating environment. Three
process observations describe repeatability over this campaign, while
long-term drift and hardware variation require separate measurements.
The original synthetic grid uses one matrix seed. The full-core follow-up
adds three matrix seeds, with one process per instance and timing mode.
The matched and native experiments each use three instances with three
processes per instance.
These chosen workloads do not define a random application population.
Historical measurements use separate protocols and are excluded from the
current averages.

The synthetic extension tests one degree-imbalance pattern. The published
matrices have artificial partitions, and the covariance component uses
eight-point partition granularity to satisfy the block-size contract.
Its startup and storage results cover a generated component rather than a
complete solver or hierarchical construction pipeline. Total storage and
setup still include matrix values and classification metadata.

Library lower envelopes favor the comparators by selecting measured medians
without charging a tuning cost. The grouped baseline is the stated slot
composition. Compatible research kernels, reordering methods, other block
ensembles, and additional precisions are outside this evaluation. The work
contributes an implementation and measured execution policy for an established
variable-block representation, with performance claims confined to the
reported comparisons.

\section{Reproducibility}
The verified Windows reference workflow uses CUDA 13.4 and MSVC 19.44.
The current build uses C++20 for host and device sources. Archived receipts
preserve the original compiler settings for earlier measurements.
From the repository root, run:
\begin{verbatim}
python scripts/prepare_application.py
python scripts/prepare_native.py
python scripts/run_final_validation.py --output-root data/rerun
powershell -File scripts/build_paper.ps1 -ResultsRoot data/rerun
\end{verbatim}
The final runner builds and tests the source, runs memcheck and filtered
racecheck, then collects the five GPU campaigns serially. Individual
runners accept fresh output directories for additional campaigns.
Run \verb|uv sync --locked| to install the Python 3.13 environment from
\path{pyproject.toml} and \path{uv.lock}, then activate \path{.venv} before
these commands. Paper building also uses pdfLaTeX and pdftotext.

\path{scripts/build_verified.py} hashes all compiled inputs before a
clean build, checks them again afterward, runs CTest, and records the
resulting executable hashes and build commands. A cached receipt is
reused only when every source and executable hash still matches. Each
campaign snapshots the source and includes this receipt, and every
process records its executable checksum. The analyzers verify the
receipt against the source archive and reject missing or mismatched
commands, matrix identities, design coverage, method counts, trial
indices, nonfinite timings, and unsuccessful processes. The hashes verify internal consistency of the archived artifacts.

Final measurements are under \path{data/product-evaluation/}, in the
\path{synthetic/}, \path{published/}, \path{native/}, and \path{ablation/}
subdirectories, with the additional seeds and queued timings under
\path{data/robustness/}. Generated tables
and figures come from these campaigns. Native geometry, partition metadata,
assembly observations, and input checksums are retained under
\path{data/native/}. Large native binary arrays are regenerated by the
preparation script and verified against their recorded checksums.
Regeneration preserves the archived assembly observations. Use a fresh
preparation directory to measure assembly again.

\path{scripts/analyze_revision.py} validates the main library campaigns.
\path{scripts/analyze_supplement.py} validates native and matched controls.
Both emit full-precision summaries beside the generated tables.
\path{scripts/build_paper.ps1} requires both analyses to pass before
compiling the manuscript. Regression tests in \path{tests/test_evidence.py}
exercise corrupt timing records and stale source or binary receipts.
The historical RHS-8 archive is validated separately for the appendix.
The two seed-4 development archives are under \path{data/narrow-tuning/}
and \path{data/narrow-tuning-2/}. Their 96 processes are validated by
\path{scripts/analyze_tuning.py} and are excluded from evaluation averages.
It predates build-linked receipts and is not used to generate current
library ratios or matched mechanism effects.

\begin{samepage}
\section{Conclusion}
VarBlockSpMM lets applications retain packed variable blocks while using a
small direct CUDA plan. Shared input tiles and multiple accumulators reuse
block data, and row ownership removes output atomics and execution workspace.
Across the additional matrix seeds,
the fastest-tested-library ratios are \RobustLatencyOverall{} for
individual products and \RobustQueuedOverall{} for batches of eight.
The width breakdown identifies where these gains justify choosing the
direct implementation.

The 64-thread narrow kernel gives paired speedups of
\RhsEightUpgrade{} at RHS 8 and \RhsSixteenUpgrade{} at RHS 16 over
the previous policy. Direct execution also avoids library-format conversion and
reduces explicit storage relative to scalar CSR on the dense-block component.
Those benefits matter when packed blocks are already available or only a
few products reuse each matrix. Compact CSR and dense SGEMM remain useful
alternatives for scalar sparsity and high overall density, respectively.
\end{samepage}

\subsection{RHS-8 mapping ablation}

then give each configuration equal weight. No significance interval is assigned.

\subsection{Earlier width specialization and profiling}
