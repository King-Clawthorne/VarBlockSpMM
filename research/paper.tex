\begin{abstract}
VarBlockSpMM computes FP32 sparse-dense products directly from dense blocks
with independently variable row and column partitions. A row-owned CUDA
kernel specializes dense panel width, reuses sparse values through multiple
accumulators, and selectively stages and double-buffers dense input tiles.
Its direct execution uses no output atomics or temporary workspace.
We evaluate the implementation on one NVIDIA GeForce RTX 5060 Ti using
128 synthetic configurations, a 40-configuration extension for matrix size
and degree imbalance, and three published structural matrices with explicit
partitions. Each configuration has three fresh process launches with randomized
method order and retained raw timings. On the core synthetic grid, geometric
speedups are \AuditCsr{} over a per-process lower envelope of four CSR
configurations and \AuditGrouped{} over cached grouped cuBLAS.
Fixed-block BSR is faster in 24 of 32 uniform configurations. Compact CSR
is faster in all twelve application matrix and width configurations under
the tested low-fill partitions. These controls separate the benefits of the execution policy from baseline
setup overhead and block fill. The results describe performance on one device.
Their relevance to applications depends on the partitions and density of
the stored blocks.
\end{abstract}

\section{Introduction}
Sparse matrices often contain dense submatrices that are useful units of
storage and computation. Fixed-size block sparse row storage exposes this
structure when all blocks have the same dimensions. Variable partitions
instead produce rectangular blocks of different heights and widths.
Scalar expansion loses explicit block reuse, while padding every block to
a maximum shape can increase storage and arithmetic.

We study \(C=AB\), where \(A\in\mathbb{R}^{M\times K}\) is a packed
variable-block sparse row matrix and \(B\in\mathbb{R}^{K\times N}\) and
\(C\in\mathbb{R}^{M\times N}\) are column-major dense panels. The supported
block dimensions are \(8,16,\ldots,64\), with independently chosen row and
column partitions. Dense panel widths are \(N\in\{8,16,32,64\}\).
The implementation uses FP32 values and accumulation for non-transpose
multiplication with \(\alpha=1\) and \(\beta=0\).

We ask when retaining dense variable blocks benefits a direct row-owned
implementation, compared with persistent library baselines that reuse metadata
and have suitable algorithm choices. We study a compact format, a
width-specialized kernel family, and a dispatch policy chosen through
measurement. The controls include fixed-block BSR for uniform blocks and
compact scalar CSR for application partitions that introduce internal zeros.

Grouping a scalar sparse matrix into dense blocks can introduce many stored
zeros. Naturally dense blocks avoid this penalty. Kernel speed alone therefore
does not establish whether packing suits the source application.

\section{Related work}
Variable blocking is established prior art. Vuduc and Moon studied variable
and unaligned blocks for sparse matrix-vector multiplication [6]. OSKI defines
variable block row storage through independent logical row and column
partitions [7]. VarBlockSpMM uses this structural model for a dense
multi-column right operand on CUDA.

GPU SpMM work has examined row assignment, load balance, instruction-level
parallelism, and reuse. Yang, Bulu\c{c}, and Owens describe row-splitting and
merge-based approaches [1]. GE-SpMM caches sparse rows and merges warps to
reduce redundant loads [8]. Tensor-core methods such as Li et al. trade
packing and preprocessing for dense matrix-instruction throughput [2].
These techniques motivate the present kernel, but this study does not
establish superiority over compatible research implementations.

The motivating application is adaptive construction of hierarchical
\(H^2\) matrices. Boukaram et al. describe a non-uniform batched BSR product
implemented through non-uniform batched GEMM operations [5]. The present
work addresses the underlying packed-block product. It does not benchmark
a complete hierarchical construction pipeline or its native partitions.

NVIDIA provides scalar and fixed-block SpMM through cuSPARSE [3], and
per-group GEMM dimensions through grouped cuBLAS [4]. These form the
library controls. Asynchronous global-to-shared copies can overlap tile
movement and arithmetic [9]. These mechanisms are established techniques. We combine and evaluate them
for this particular variable-block operation.

\section{Representation and kernel}
Let block-row boundaries be \(r_0<\cdots<r_R\), and block-column boundaries
be \(c_0<\cdots<c_Q\). Block \((i,j)\) has height
\(h_i=r_{i+1}-r_i\) and width \(w_j=c_{j+1}-c_j\). Its column-major values
are packed without rounding its dimensions to a global block size, and its
contribution is
\[
C[r_i:r_{i+1},:] \mathrel{+}= A_{ij}B[c_j:c_{j+1},:].
\]
Block-row pointers and column indices locate the blocks. Scalar offsets and
value offsets are 64-bit. Block indices remain 32-bit. Host validation checks
monotonic offsets, dimensions, index bounds, and payload sizes. A matrix owns
its GPU storage and row classifications. Execution plans hold non-owning
views, so the matrix must outlive its plans.

\subsection{Output ownership and accumulation}
For RHS 16, 32, and 64, one cooperative thread array, or CTA, owns one
block row. RHS 8 launches two 256-thread CTAs per block row to cover disjoint
output tiles of the maximum 64-by-8 panel. Threads outside the actual row
height do no output work. Threads accumulate every block contribution before
writing their outputs once. Different CTAs never update the same scalar, which
removes the need for output atomics or partial-output reduction storage.
The mapping also makes performance sensitive to work imbalance between rows.

RHS 8 uses one output element per thread. RHS 16 and 32 use eight output
columns per thread, and RHS 64 uses sixteen. Each loaded sparse value
therefore feeds several independent multiply-add operations. This reduces
redundant requests for sparse values at the cost of more registers and fewer
independent threads.

\subsection{Staging and dispatch}
For RHS 32 and 64, every local output row consumes the same dense input tile
for a stored block. Cooperative staging loads this tile once per CTA and
reuses it across local rows. A shared leading dimension of 65 floats reduces
power-of-two bank-alignment conflicts. The synchronous RHS-32 and RHS-64
kernels use 8,320 and 16,640 shared-memory bytes per CTA, respectively.
RHS 16 retains direct loads because its smaller reuse opportunity did not
repay the measured synchronization cost.

For RHS 32, rows of at most 16 scalars use a 128-thread single-buffer CTA.
Taller rows use a 256-thread CTA with two tiles, consuming 16,640 shared-memory
bytes. The next input tile is prefetched before arithmetic on the current
tile. Pipeline waits and CTA barriers protect visibility and buffer reuse.
A mixed-height matrix is split into two launches only when its mean block
degree is at least eight. Homogeneous matrices need only the applicable
launch. At lower mean degree, the mixed matrix uses the unsplit policy.

Double buffering is not enabled for RHS 64. A development experiment increased
shared allocation to about 32.5 KiB per CTA and regressed a representative
median from 2.891 to 4.419 ms. This observation motivated a width-specific
policy rather than a universal pipeline. All dispatch thresholds were chosen
from earlier development sweeps and held fixed for the revision experiments.

\section{Experimental design}
\subsection{Persistent library controls}
\textbf{Scalar CSR.} Synthetic dense blocks are expanded into scalar CSR
once. Plans retain arrays, descriptors, handles, and workspace. We measure
the default algorithm, explicit CSR algorithm 1 with preprocessing,
algorithm 2, and algorithm 3 with preprocessing. All use FP32 compute,
column-major panels, and the same non-transpose operation. Preprocessing and
initial descriptor creation occur during setup or warmup, outside timing.
NVIDIA documents preprocessing benefits for algorithms 1 and 3 [3].

The \emph{CSR lower envelope} is the minimum GPU median among those four
configurations within each process. Selecting on measured data favors this comparator. The envelope has no
deployed tuning policy or charged tuning cost. It lets us check whether
a direct-method win depends on the default library algorithm. Host ratios use a separate
minimum over host medians, so they need not select the same algorithm.

\textbf{Grouped cuBLAS.} Blocks with equal height and width are grouped within
each ordinal block slot. A slot contains at most one block from each row, so
its GEMM outputs do not overlap. Slots execute sequentially. The first uses
\(\beta=0\), and subsequent slots use \(\beta=1\). The handle, packed values,
shape groups, and device pointer arrays persist.

The cached control refreshes input and output pointer arrays only when their
base addresses change. It omits the full output clear when every row is
nonempty. For matrices containing empty rows it retains the clear to initialize
those rows. A separate changing-address experiment alternates between two
allocated input/output pairs and includes pointer refreshes. It is paired
with a direct method that alternates the same pairs. Pointer contents are
rebuilt on the host and copied on the execution stream when needed.
The first measured call reuses the final warmup addresses. The remaining
19 calls alternate addresses and refresh the grouped pointers.
Further optimization of pointer marshaling may improve this library
composition.

\textbf{Fixed-block BSR.} The uniform-32 synthetic subset is also measured
with cuSPARSE BSR algorithm 1. Block values are converted to the required
row-major block layout outside timing, while dense panels remain column-major.
This gives a format-matched control where variable blocking is unnecessary.

\subsection{Synthetic workloads}
The core grid contains 128 configurations with 4,096 block rows and columns,
degrees \(2,4,8,16\), four panel widths, four size distributions, and two
locality patterns. Uniform uses size 32. Low variance samples
\(\{24,32,40\}\), high variance samples \(\{8,16,\ldots,64\}\), and bimodal
samples \(\{8,16,48,64\}\). Row and column dimensions are drawn independently.
Every row in the core grid has exactly the requested degree. Columns are
sampled without replacement and sorted. Random locality spans all block
columns. Local locality samples cyclic offsets within plus or minus the
requested degree. Stored values are uniform on \([-1,1]\).

The extension adds 40 configurations. It evaluates 256, 1,024, and 4,096
block rows and columns for high-variance and bimodal sizes, random locality,
all panel widths, and either constant degree 16 or the repeating degree pattern
\(0,1,16,16\). The latter has mean degree 8.25 and explicitly includes empty
rows. It is constructed by retaining zero blocks, one block, or all blocks
from successive rows of the degree-16 parent matrix. Eight constant-degree
4,096-row configurations already belong to the core grid. Thus the union
contains 168 unique configurations.

The synthetic campaign holds matrix seed 1 fixed and repeats each configuration in
three fresh processes. The dense input contains independent pseudorandom
uniform values on \([-1,1]\), generated with seed 9123. Changing-address
buffers contain identical values to isolate address-dependent work.

\subsection{Published matrices and partitioning}
We also test BCSSTK13, BCSSTK14, and BCSSTK15 from the Harwell-Boeing
collection, downloaded through SuiteSparse [10]. They originate from fluid-flow
eigenvalues, the Omni Coliseum roof, and an offshore platform module,
respectively [11]. Their original orders are 2,003, 1,806, and 3,948.

Symmetric Matrix Market input is expanded, duplicates are combined, and
explicit zeros are removed. Values are divided by the maximum absolute
entry and converted to FP32. The rows and columns are padded only at the
outer boundary to the next multiple of eight. In the original scalar ordering,
row partitions cycle through \(8,16,32,64\) and column partitions through
\(64,32,16,8\). The final partition is truncated to the remaining multiple
of eight. A block is stored if it contains a source nonzero. Other entries
inside that block are represented as zeros.

This deterministic procedure preserves application-derived values and
sparsity after normalization, but uses artificial partitions in place of native
finite-element or hierarchical partitions. The measured compact-CSR controls retain only
source nonzeros in the padded scalar domain, using explicit algorithms 1,
2, and 3 with preprocessing for 1 and 3. Their lower envelope is computed
as above. Cached grouped cuBLAS uses the identical packed blocks as the
direct method. This separates the cost of block fill from scalar sparse
execution. All four panel widths and three fresh processes are retained.

\subsection{Timing and correctness}
Each method receives five warmups and 20 measured executions. Methods are
randomly ordered within each process. Configuration and process-label jobs
are shuffled before serial execution, with one GPU benchmark active at a
time. Synthetic order uses seed 20260905 and application order uses 20260906.
Three process labels identify repeated observations of the same matrix,
rather than three different matrix instances.

CUDA events bracket each execute call on the default stream, followed by an
end-event synchronization. Synchronized host durations are also retained.
The intervals measure execution calls, including any device idle time while
the host submits later work. This matters particularly for library compositions
with multiple calls, so the intervals do not isolate kernel-instruction time.
Allocation, format conversion, initial input transfer, and correctness
validation are excluded. Every raw GPU and host duration, method position,
command, and process status is saved. Medians use the mean of the two middle
observations for an even sample count.

The revision uses the RTX 5060 Ti with compute capability 12.0, CUDA runtime
and driver API 13.4, Windows, MSVC 19.44, Release compilation, native CUDA
architecture, and fast FP32 math. The Windows display driver reports version
32.0.16.1664. The GPU is not clock-locked or isolated from all operating-system
activity. Per-process environment records accompany the synthetic timings.

The correctness suite covers both localities for every combination of four
size distributions, four widths, and degrees \(1,4,8,16\), giving 128 cases.
Sixteen additional cases contain an empty first row. It tests explicit CSR
algorithms, uniform BSR, cached pointer reuse and address changes, and
non-default streams. Full output is compared with a double-accumulating CPU
reference. Failure thresholds are maximum absolute error \(5\times10^{-4}\)
or relative \(\ell_2\) error \(5\times10^{-5}\), with NaN and infinity rejected.

Each timed synthetic matrix also receives 64 CPU output probes per method
outside timing. Every application output is checked against a separate
compact-CSR CPU reference, which also tests the packing transformation.
The expanded test executable also passes Compute Sanitizer memcheck with
zero reported errors. Racecheck restricted to the project's row-owned kernels
reports zero hazards. Library kernels are outside that racecheck filter.
These checks do not substitute for sanitizer coverage of every timed configuration.

\subsection{Aggregation and uncertainty}
For configuration \(c\), process label \(p\), comparator \(b\), and direct
method \(d\), let
\[
 y_{c,p}=\log\left(t_{b,c,p}/t_{d,c,p}\right),\qquad
 g_c=\exp\left(\frac{1}{3}\sum_{p=1}^{3}y_{c,p}\right).
\]
The reported geometric mean is
\(G=\exp(|\mathcal C|^{-1}\sum_{c\in\mathcal C}\log g_c)\).
Each configuration and each process within it has equal weight. Ratios
above one favor the direct method. Minima and win counts refer to the
configuration ratios \(g_c\), not to individual timing trials.

We also report the range of three aggregate ratios obtained by holding the
process label fixed. This is a descriptive repeatability check, not a
confidence interval or a test of significance. Three process observations
provide limited information about tails and shared thermal drift. No
population-level confidence interval is assigned to this deliberately chosen
grid, and no comparison of interval widths is interpreted as a decomposition
of uncertainty. Matrix-instance variation, workload selection, process noise,
and hardware variation remain distinct questions.

\section{Scope and limitations}
The implementation processes packed blocks directly through width
specialization, value reuse, and a staging policy chosen through measurement. The absence of output atomics and execute-time temporary
workspace follows from row ownership. It does not imply that matrix storage,
classification metadata, or setup is free.

All measurements use one GPU and one local operating environment. Three process observations improve the
protocol but cannot characterize long-term drift or hardware variation.
The synthetic campaign fixes one matrix seed. The historical
five-seed study varies instances under a different protocol and cannot be
combined with it as additional process repetitions.

The core synthetic rows have constant degree, and the extension adds one
particular imbalance pattern. The three published matrices use explicit,
artificial partitions and are small relative to the main synthetic grid.
They do not substitute for native dense variable blocks from an \(H^2\)
application. Setup time, storage totals, and amortization over repeated
products are not benchmarked as end-to-end application costs.

The CSR lower envelope favors the comparator through selection on measured
medians. The grouped implementation is a concrete slot-based composition,
not an exhaustive optimization of grouped GEMM. Compatible research kernels,
reordering methods, alternative block ensembles, and additional precisions
remain outside the comparison. The results describe the tested regimes. They establish neither
state-of-the-art performance nor a new sparse format.

\section{Conclusion}
VarBlockSpMM implements packed variable-block FP32 SpMM with disjoint output
ownership and selective dense-tile reuse. The evaluation uses cached grouped pointers, explicit CSR algorithms,
preprocessing, and fixed-block BSR controls. Methods run in randomized order
across fresh process launches, and all raw timings are retained. Its core-grid geometric ratios are \AuditCsr{} over
the CSR lower envelope and \AuditGrouped{} over cached grouped cuBLAS.

Representation choice affects the result. The tested variable partitions
introduce substantial internal zeros in published scalar sparse matrices.
Their comparison with compact CSR must therefore remain separate from
results for naturally dense synthetic blocks. Application-native
partitions are needed to test whether that storage penalty can be avoided.
BSR also wins most uniform cases, so the direct method should be evaluated
as a specialized variable-block option alongside format-matched alternatives.
Tests on additional GPUs and native application partitions are needed to
establish where this policy is useful beyond the measured settings.
