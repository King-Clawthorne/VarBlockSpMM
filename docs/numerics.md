# Numerical behavior

Each output entry is a sum of products, evaluated as FP32 multiply-add with FP32 accumulation, in an **unspecified order**, with no double accumulation and no compensated summation. The device sources are compiled with `--use_fast_math`, which implies [`-ftz=true`](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/#ftz-flush-to-zero-ftz), and flush-to-zero applies **per instruction**, to that instruction's inputs and to its rounded result. It does *not* apply to the product term inside a fused multiply-add, which is computed exactly and added to the accumulator before a single rounding: `fma(FLT_MIN, 0.5, FLT_MIN)` retains `1.5 * FLT_MIN`. Three consequences follow, none of which you can rule out by inspecting your inputs:

- **Intermediate underflow.** Any instruction input, or any accumulator value an instruction produces, that lands in the subnormal range becomes zero, so contributions that pass through a subnormal accumulator are lost. Two contributions of `FLT_MIN * 0.5` have normal operands and an exact sum of `FLT_MIN`; this library returns `0`, because each multiply-add produces a subnormal result from a zero accumulator. The largest subnormal times `2^126` returns `0` for the other reason: the operand is flushed on input.
- **Intermediate overflow.** A partial sum above `FLT_MAX` becomes an infinity and propagates even when the exact sum is finite. Because the order is unspecified, a later cancelling term cannot be relied on to rescue it.
- **Cancellation.** Error grows with the number of terms and with cancellation between them, as in any uncompensated FP32 summation.

This is a description of what the library computes, not a guarantee of agreement with a double-accumulated reference. What is verified is narrower: on the tested workloads, results agree with such a reference with both maximum absolute error at most `5e-4` and relative L2 error at most `5e-5`.

`tests/test_numeric_range.cpp` pins each behavior above, including the multi-contribution underflow, overflow, and cancellation cases, not just single products. `tests/test_input_subnormals.py` records which prepared inputs actually contain subnormal packed values: the three clustered 2,048-point covariance matrices contain 162, 212, and 294 of them, and every other prepared input contains none. Their combined magnitude is below `1e-30` of each matrix's total, so their numerical contribution is negligible and the measured outputs pass the stated correctness checks. That bounds what flushing changes in the values, not in the time: no measurement here compares flush-to-zero against gradual-underflow execution. These suites do not establish agreement with an IEEE 754 gradual-underflow implementation. If your values reach the subnormal range, rescale them or rebuild without `--use_fast_math` in [CMakeLists.txt](../CMakeLists.txt), and rerun `ctest` to see the numeric-range test report the change.
